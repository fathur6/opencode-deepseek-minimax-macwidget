<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User secure-field input → provider validator | An untrusted candidate key may travel only to the chosen provider's existing HTTPS validation endpoint. |
| Validator → Keychain | A success result may authorize a per-provider encrypted replacement, while stale/failure results may not. |
| Codex auth file → Settings UI | The UI learns connection availability without receiving or displaying a token. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-08 | Tampering | ProviderSetupCoordinator | high | mitigate | Validate before upsert, retain existing entry on failure, and enforce independent per-provider generation checks tested with delayed validators. |
| T-05-09 | Information Disclosure | Settings UI and coordinator | high | mitigate | Secure fields, status-only observable state, redacted errors, injected fake tests, and no credential/token persistence outside Keychain. |
| T-05-10 | Elevation of Privilege | Codex guidance | high | mitigate | Pasteboard-only fixed command and tests with no process dependency or OpenAI key-entry control. |
| T-05-11 | Denial of Service | native Settings | medium | mitigate | Use SwiftUI Settings/SettingsLink rather than custom window ownership; keep Keychain work off MainActor and content scrollable in a bounded window. |
| T-05-SC | Tampering | package installation | low | accept | No npm, pip, cargo, or third-party package installation is planned. |
</threat_model>
